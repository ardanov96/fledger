# ADR-0002: sqlc over GORM/ORM

**Status:** Accepted
**Date:** 2026-08-10
**Deciders:** Project lead
**Tags:** database, sql, code-generation

## Context

We need a database access layer for PostgreSQL. The ledger has critical queries that use:

- `SELECT ... FOR UPDATE` row-level locks (ADR-0004)
- `INSERT ... RETURNING`
- Complex JOINs and aggregations for aging reports
- Window functions for trial balance
- Exclusion constraints via `btree_gist`

We need full control over the SQL emitted. Some queries are too important to be hidden behind an ORM's auto-generation.

## Options Considered

| Option | Pros | Cons |
|---|---|---|
| **sqlc** ✅ | Type-safe generated Go from raw SQL; full SQL control; small runtime; great for hand-written queries | Limited for very dynamic queries; build step required |
| **GORM** | Familiar, fast CRUD, auto-migrations, hooks | Hides SQL, "magic" behaviors (e.g. soft deletes), poor for complex queries, harder to reason about locking |
| **Ent** | Graph-based schema, type-safe, code generation | Steep learning curve, opinionated, locks you into a specific schema model |
| **sqlx** | Lightweight, hand-written SQL | No type safety, manual struct scanning, easy to drift |
| **Database/sql + manual** | Maximum control, no deps | Most boilerplate, no type safety, easy to introduce bugs |

## Decision

**Use sqlc** to generate Go code from raw SQL files in `internal/repository/postgres/queries/`.

## Rationale

- **SQL is the source of truth.** The actual SQL — including `FOR UPDATE` clauses, `RETURNING`, and locking hints — is the artifact we review. With an ORM, the SQL is generated and rarely inspected.
- **Type safety at the Go layer.** sqlc generates structs and methods from query comments. No `interface{}` or manual scanning.
- **Locking is explicit.** `SELECT ... FOR UPDATE` is visible in the query file, not buried in a callback chain.
- **Audit-friendly.** When explaining a query to an interviewer or auditor, we can show the exact SQL.
- **Zero runtime overhead.** No reflection, no query building, no N+1 surprises.
- **Testable in isolation.** Each query can be unit-tested against a real Postgres (via testcontainers) without bringing up the application.

## Consequences

### Positive
- Full SQL control — no ORM footguns (N+1, lazy loading, hidden transactions).
- Migrations are plain SQL — no language-specific migration tool.
- Generated code is small, fast, and reviewable.
- Queries are first-class artifacts; easy to grep, search, refactor.

### Negative
- Build step (`make sqlc-gen`) — devs must install sqlc.
- Dynamic queries (e.g. optional filters) require hand-rolled SQL with `COALESCE` or `sqlc.narg`.
- Migrations are still managed separately (golang-migrate).
- No automatic "load relations" — must JOIN explicitly.

## Implementation Notes

```
internal/
  repository/
    postgres/
      queries/
        accounts.sql      # all account queries
        entries.sql       # all entry queries
        transactions.sql  # all transaction queries
      account_repo.go     # generated by sqlc
      entry_repo.go       # generated by sqlc
      transaction_repo.go # generated by sqlc
      db.go               # generated by sqlc (DB connection wrapper)
sqlc.yaml                 # sqlc config at repo root
```

### Example query file

```sql
-- name: LockAccountForUpdate :one
-- Locks an account row for update within a transaction.
SELECT id, code, name, type, status, currency, cached_balance, owner_id, tenant_id, created_at, updated_at
FROM accounts
WHERE id = $1
FOR UPDATE;
```

### Workflow

1. Write/modify SQL in `queries/`.
2. Run `make sqlc-gen` to regenerate Go.
3. Update interface implementations in domain layer if signatures change.
